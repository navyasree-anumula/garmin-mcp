# v1.7 candidates — a proposal, not an amendment

**Status: PROPOSAL for Mahi. Nothing here is ratified and nothing here is built.**

This is the input to a SCOPE amendment, not the amendment. Once Mahi picks a set, **that set**
gets the ten dimensions of `sop/stress-test-10-dimensions.md` plus passes A and B before any code
is written — which is the order v1.6 got wrong and §15.1 recorded (two of its three items shipped
before the document authorised them).

Everything below is drawn from `docs/journal.md`'s open checks and pending decisions and from
SCOPE §15. Nothing is invented for this list.

## 2. Free to settle — no code, no version, do these first

These cost minutes and retire real uncertainty. Nothing below needs a release.

1. **The four unverified metric rows** — `training_status`, `load_balance`, `readiness`,
   `recovery_time`. Settle the way `hrv_status` was: compare each row's output against what the
   Connect **app** displays for the same day. `probe --explain` cannot do it — it prints value
   types, never values. This retires four of nine map rows and is the highest value per minute on
   the whole list.
2. **The update path, live (open check 4).** The biggest untested surface in the write path. Every
   live create so far has taken the **upload** branch: no match ⇒ `upload_workout` ⇒
   `schedule_workout`. The other branch — match ⇒ read the target month ⇒ `update_workout` in
   place ⇒ skip or schedule — is **four code paths and one Garmin behaviour that have never been
   near a real account.** And it needs no artificial test: it *is* the normal weekly
   re-prescription. Create the same-named circuit on a different date and expect
   `action: "updated"`, the **same** `workout_id`, `requests_made: 4`, `scheduled: "new"`. Then a
   third create on a date it already holds, expecting `scheduled: "already"` and **no second
   calendar entry**.
3. **The off-pace alert** — the 1 Nov run. Not load-bearing any more (the pace data is confirmed
   correct), but it is the last thing standing between "Garmin stored it" and "the watch acts on
   it".
4. **Delete the throwaways from Connect** — `throwaway test` (workout 1742892340 and its calendar
   entry) and the two 1 Nov sessions once they have served their purpose. There is no delete tool

## 3. The recommended v1.7, and why this shape

**Recommendation: keep v1.7 to the committed floor plus two cheap decisions.** Scope discipline is
the binding constraint — a session's review should take no more than twenty minutes — and v1.6's
review was already at the edge with three items.

### v1.7 = "the write path becomes reversible, and the docs stop lying"

- **Unschedule-by-lookup** (code, committed)
- **The three carried debts** (docs, committed)
- **The §5 tool-split decision** (one line, below)
- **The CI two-liner** (below)

**Why unschedule leads.** Every write this server has made is currently **un-undoable except by
hand in Connect**, and that stopped being theoretical today: two real sessions are on the calendar
for 1 Nov. `unschedule_workout` takes the scheduled id and nothing else, and the id has been
dropped by summarising clients five times. A write path that cannot be reversed from the same
conversation that created it is the sharpest remaining gap, and it is the gap the §9 risk row was
opened for.

**Why the docs debts ride along rather than waiting again.** They were deferred twice as a scope
decision; a third deferral was named a debt. v1.7 now has a code item, so it is no longer the
docs-only version that slips because nothing in it blocks.

### The two cheap decisions, each one line of judgement

- **§5 tool-split — ratify or reject.** `garmin_workouts` (preview, read-only) and
  `garmin_workout_create` (write) ship as two tools because `ToolAnnotations` are per tool and §5
  asks for per-action honesty. **§5 never mentions the split, so the code and the document
  disagree**, and v1.6's ratification did not touch it. Ratifying costs a sentence in §5;
  rejecting costs the preview its `read_only_hint`. **Recommend ratify** — the annotation is only
  honest if it is per action, and it already ships that way.
- **CI hygiene, two lines in `docker.yml`.** `paths-ignore: ['docs/**']`, confirmed needed on
  2026-10-31 when the docs-only merge of #38 ran a full multi-arch build and moved `latest` to a
  tag whose application code was identical to the previous one — note this also means `latest`
  would point at the last **code** commit rather than `main`'s tip, which is a decision and not a
  cleanup. And `ignore-error=true` on `cache-to`, which turns the `failed to reserve cache` flake
  into a warning instead of a red check; it hit two PRs in one evening.

## 4. Deferred to v1.8 — worth building, not worth crowding v1.7

In rough order of value.

1. **Reps and weight for strength.** The only prescription axis still missing: v1.6 prescribes a
   circuit by time only. Upstream supports both (`create_strength_exercise_step` takes `reps` and
   `weight_kg`, and Garmin stores `weightValue` in **grams** tagged with a kilogram unit — a trap
   worth a test). Left out of v1.6 deliberately because every kind offered is a kind the live
   cycle has to confirm, and that argument still holds: this is one live create's worth of risk.
2. **Cassettes (§8).** Required by §8 and still unbuilt. The transport is now known: writes go
   through `requests` via `_api_session` and **are** recordable; login is `curl_cffi` and is not,
   so the password POST cannot reach a cassette. Needs `filter_headers` for
   `Authorization`/`Cookie`, a `before_record_response` (a near-expiry `_refresh_session()`
   carries tokens), and a test asserting **no cassette on disk holds a token-shaped string** —
   with a positive half driving a synthetic token through the real scrubber, because that
   assertion passes vacuously while the cassette directory is empty. `vcrpy` is not yet a
   dependency, though `tests/test_runtime_lock.py` already lists it as dev-only.
3. **`tools.json` and `garmin_auth_status` reporting the live tool set.** The env-var gate answers
   the exposure question for now; the exposure set and a tool that reports what is actually
   exposed remain §5's design.
4. **The provenance question.** The qualifier on an unverified row does not reach a summarising
   reader. Two options: refuse unverified rows outright, or move the qualifier out of `note` and
   into `verdict` as a fifth value, `present_unconfirmed`. **This is the same failure class as the
   dropped ids** — a field returned is not a field delivered — so it is worth solving once in a
   way that covers both.
5. **Body battery.** Measured and deliberately unmapped: it arrives inside the stress payload as a
   descriptor-indexed positional array and needs a decoder resolving a descriptor key to a
   position. A row written before that decoder exists is a guess.

## 5. Not features, but on the board

- **`id_keys` — keep or remove.** Argued as schema rather than account data, by analogy with
  `probe --explain`. Remove it if Garmin's response key names read as account information.
- **The cron's failure mode is silence.** Public-repo scheduled workflows auto-disable after 60
  days of inactivity with no documented notification.
- **The pace block's `displayOrder`** — unverified and **inert**. Nothing observed depends on it
  and a wrong value would not show in Connect or on the watch. Labelled, not promoted.
