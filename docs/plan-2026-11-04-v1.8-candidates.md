# v1.8 and v1.9 — the weekly loop reads, and two reversals at the write boundary

**Status: the SET IS DECIDED by Mahi in-session 2026-11-04, and step 0 has RUN (§2). Nothing
here is built, and this document is not the SCOPE amendment.** It is the input to one. Each session below gets the ten
dimensions of `sop/stress-test-10-dimensions.md` plus passes A and B **before its own code** —
per session, not once for this document, because A, B and C touch different state and a single
walk across all three would be the broad-and-shallow review v1.6 got wrong (§15.1).

What this version exists to serve, stated before the items so the priority order can be argued
against something: **an 8-week plan built one week at a time, with a feedback check-in before each
new week** — three runs (Mon/Thu/Sat) and two strength sessions (Tue legs, Fri upper). The loop
needs four things the server cannot do today: see what was actually done against what was
planned, trust the readiness number, read one call instead of seven at the check-in, and keep an
easy run genuinely easy.

**Provenance, as always.** Every claim below carries how it is known. `measured` means read off a
real payload or a real page. `read from the library` means read off `garminconnect 0.3.11` as
installed in `.venv` — which is evidence about *our call shape*, never about what Garmin returns.
`assumed` means nobody has checked. The point of the labels is that §4's walks and the live checks
know what they are for; a plan whose claims are all in the indicative gives them nothing to do.

## §2 Step 0 — RUN 2026-11-04, and what it settled

`garmin-mcp probe --explain training_readiness,heart_rate_zones,activities` ran on the laptop and
all three endpoints answered. The output is **key paths and value types only — no value printed or
stored**, which is the property that let it be pasted into a session at all (§8). It retired most
of the assumptions this document opened with, **and it falsified this document's own diagnosis of
B.** §5 had owed the activities half since v1.4: *"the probe has only ever called the activity
list… phase 5c probes it before the tool is designed."*

### §2.1 Readiness: the field names were right. The decoder is what is broken.

`score: int` and `recoveryTime: int` are **exactly the paths the map already carries**
(`metrics.py:141-172`), and the endpoint reported HAS DATA with 26 populated fields. So **both**
hypotheses this document was built on are dead: no field name was invented, and Garmin did not
return an empty envelope.

**The defect is one line below the path.** `latest_by_timestamp` keeps only snapshots whose
timestamp is numeric —

```
if isinstance(snap.get(key), int | float)      # extract.py:110
```

— and the probe shows `timestamp: str`. Every snapshot is filtered out, `stamped` is empty, the
decoder returns `MISSING`, and both rows report `no_data` **against a payload that holds the
data**. The map's note recorded that selection is by timestamp *rather than by index*; what
nobody recorded is the timestamp's **type**. An inferred type is exactly as unsourced as an
inferred name, and this document priced the risk in the wrong half of the row.

Two further readings, neither of them what was being looked for:

- **The root is `list(1)`, not the `list(4)` recorded in 5b.** Four snapshots a day is a property
  of one response, not of the endpoint — which is precisely why the decoder picks by timestamp
  instead of by position. The decoder's *reason* survives; only its type check fails.
- **`level: str`, `feedbackShort: str` and `feedbackLong: str` sit in the same payload.** Garmin's
  own words for readiness, free, out of a request already being made. §5 prefers Garmin's phrase
  to a number whose scale cannot be sourced — so **the scale stops being load-bearing**: the
  phrase can answer the question while the score keeps its honest `"index, scale unconfirmed"`.
- Also in there and worth a later look, not a change now: `acuteLoad`, `hrvWeeklyAverage` and
  `sleepScore`, which are **second sources** for rows the map already fills from three other
  endpoints, plus six `*FactorPercent` / `*FactorFeedback` pairs that say *why* readiness is what
  it is. A second source can disagree with the first, so each would have to name itself — §5's
  rule, and the reason this is a note rather than a free win.

### §2.2 Zones: everything D needs, in one request, with one inference left

`get_heart_rate_zones()` answered `list(1)` with `zone1Floor` … `zone5Floor`, `maxHeartRateUsed`,
`lactateThresholdHeartRateUsed`, `restingHeartRateUsed`, `trainingMethod`, `sport`,
`restingHrAutoUpdateUsed` and `changeState`.

- **Max HR and threshold HR are both in this payload**, so `get_lactate_threshold` and
  `get_user_profile` are **not needed**. B is one request, and the "max HR might live elsewhere"
  assumption is retired.
- **The zones are floors.** Zone N runs from `zoneNFloor` to `zone(N+1)Floor`, and **zone 5's
  ceiling is inferred to be `maxHeartRateUsed`** — the single arithmetic step no field gives, and
  the only inference in D's converter. It is division and subtraction over Garmin's own numbers,
  so it is not the training science §1 forbids, but it gets a test and a label.
- **`trainingMethod` says how the zones were computed** — percentage of max, of threshold, or of
  reserve. It is a phrase and it is kept: the same zone number means different bpm under a
  different method, so a converter that silently assumes one is the HR version of the pace
  bound-order risk.
- **`list(1)` is one sport profile, and which sport it is was not printed** (it is a value).
  Upstream's docstring says "all sport profiles"; this account returned one. D needs the
  **running** profile, so the tool reads `sport` and refuses rather than assuming the single row
  is the one it wants.

### §2.3 Activities: the link is real, and the exposure is not the one §9 names

- **`workoutId: int` is present** — so planned-versus-done is a real link and not a name-and-date
  match. This was the single assumed field the whole feature rested on. What is still unmeasured
  is the *negative* case: whether an activity with no scheduled workout omits the key or carries
  a zero.
- **`hrTimeInZone_1` … `hrTimeInZone_5: float` are in the LIST.** "Was the easy run actually
  easy" is therefore answerable in **session A**, from one list call, with no detail request and

  two sessions early.
- **`averageSpeed: float`** means pace reuses the existing metres-per-second conversion rather
  than a second pace formatter.
- `aerobicTrainingEffect`, `anaerobicTrainingEffect`, `trainingEffectLabel` and
  `activityTrainingLoad` are all present, as are `averageHR`, `maxHR`, `distance`, `duration`,
  `movingDuration`, `activityType.typeKey` and `startTimeLocal`.
- **Per-lap HR is still not in reach.** `lapCount` and `hasSplits` are there, but `splitSummaries`
  is an **aggregate per split type** — `noOfSplits`, `duration`, `distance`, `averageSpeed` — and
  **carries no HR at all**. So `detail` still needs `get_activity_splits`, which remains unprobed.
- Noted for the reps-and-weight deferral, not for building: `summarizedExerciseSets[]` carries
  `category`, `reps`, `sets`, `volume`, `maxWeight` and `duration`. Garmin **reports** what a
  strength session actually did, including reps and weight, even though v1.6 prescribes by time.

**The exposure finding, and it is not location.** Every row of the list carries `ownerId`,
`ownerDisplayName`, `ownerFullName` and three `ownerProfileImageUrl*` fields, plus
`userRoles: list(38)`, `privacy.typeKey`, `deviceId` and `timeZoneId`. **`ownerDisplayName` is
the GUID §10 calls load-bearing and deliberately does not record, because this repository is
public.** The allowlist in §3.2 was argued for coordinates; it is now **required for identity**,
which is a different risk from the one §9 is about to grow a row for. `timeZoneId` is a coarse
location signal and is not returned: `startTimeLocal` already gives the weekly loop the local
date it needs.

**What step 0 did NOT settle about location — the over-reading to avoid.** The probed payload
carries **no coordinate field at all**: no `startLatitude`, no `locationName`, no polyline. It
would be wrong to promote that to "the activity list is coordinate-free". `get_activities(0, 1)`
returns **the most recent activity, whatever it happens to be**, and this one is a strength
session — it carries `summarizedExerciseSets`, `totalReps` and `activeSets` — so it had no
coordinates to carry in the first place. It does carry `hasPolyline: bool` and `hasHeatMap: bool`,
which says geometry is *referenced* from the list. **A GPS run is the case that matters, and it is
still unmeasured.**

## §3 v1.8 session A — past activities, without the GPS

**Mahi's highest priority, and the half of the weekly loop that is entirely missing: planned
versus done is unknowable from this server today.**

### A.1 The contract

One tool, two actions. Both are read-only and idempotent, so one tool's annotations are honest
for both — which is the test the §5 tool split (ratified 2026-11-02) actually applies, rather
than "one tool per endpoint".

```
garmin_activities(action="list", start_date, end_date, sport=None)
garmin_activities(action="detail", activity_id)
```

**`list` returns, per activity:** `activity_id` (so `detail` can be asked for), the local start
date and `date_basis`, type, name, distance with its unit, duration with its unit, average pace
in min/km, average and maximum HR, aerobic and anaerobic training effect where present, and
`workout_id` where the activity came from a scheduled workout. Plus `requests_made`.

**`detail` returns** per-lap splits: lap number, distance, duration, pace, average and maximum HR.

### A.2 Privacy — two risks, and §9 has a row for neither

§9 names credentials and health data and is **silent on location**; `get_activity_details`
returns polylines, and that silence is the carried debt (deferred four times, §16.3). **Step 0
found a second exposure in the same payload and §9 is silent on that too: account identity** —
`ownerDisplayName` (the load-bearing GUID of §10), `ownerFullName`, `ownerId` and three profile
image URLs, in every row of every list. So the amendment owes §9 two rows, not one. A's answer
has three layers, and the first one is the real one:

- **Do not ask for the track.** `get_activity_details(id, maxchart, maxpoly)` validates `maxpoly`
  with `_validate_non_negative_integer`, so **`maxpoly=0` is an accepted argument** (read from the
  library, `__init__.py:2957-2969`). Whether Garmin then returns no polyline is **assumed** and is
  one of A's live checks. Better still: the tool does not call `get_activity_details` at all unless
  the probe shows it is the only source of lap HR.
- **An allowlist, never a denylist.** The projection names the fields that may leave; anything
  else is dropped. A denylist leaks the next field Garmin adds — and step 0 showed the list
  payload has **over a hundred keys**, nine of which nobody would have thought to deny. Named
  exclusions that must be in the test rather than only in prose: `startLatitude`,
  `startLongitude`, `endLatitude`, `endLongitude`, `locationName`, any `geoPolylineDTO`,
  `ownerDisplayName`, `ownerFullName`, `ownerId`, `ownerProfileImageUrl*`, `userRoles` and
  `timeZoneId`.
- **The test needs a positive half.** An assertion that the output holds no coordinates passes
  vacuously against a fixture that has none — and the fixture step 0 would have produced has
  none, because the activity it read was indoors. So one fixture carries synthetic coordinates, a
  synthetic location name **and a synthetic owner GUID** through the real projection, and the
  assertion is that none of them come out — the lesson the cassette scrubber (§8, deferred) was
  written down for.

`startTimeLocal` **is** returned and is not treated as location: the weekly loop needs the local
date to line a session up against what was planned, and a timestamp is not a place.

### A.3 Mechanism, and the cost

| Step | Call | How it is known |
|---|---|---|
| List a window | `get_activities_by_date(start, end, activitytype=None)` | read from the library, `__init__.py:2624` |
| One activity's laps | `get_activity(id)` — *"summary, including basic splits"* — then `get_activity_splits(id)` | read from the library, `__init__.py:2949`, `2873`. Step 0 ruled the **list** out as a source: `splitSummaries` aggregates per split type and carries no HR. Which of the two detail calls has per-lap HR is still **assumed**, pending step 0b |

**Request cost.** `get_activities_by_date` pages 20 at a time and stops on the first empty page,
so a week of five sessions is **2 requests** — one page plus the empty page that ends the loop
(inferred from the code at `__init__.py:2664-2679`, not measured live). The probe's warning that
this method "paginates up to MAX_PAGINATED_REQUESTS (2000) with no delay" (`probe.py:192`) is
about the **unbounded** case, not about a one-week window; the bound still belongs in our layer,
because a wide window is a scrape and §6 exists to make scrapes impossible.

**So: the range is capped, and the refusal names the cap.** A bounded refusal beats a silent
partial — this repo's own rule, learned on the page cap.

### A.4 What A must settle live

- ~~Does an activity carry `workoutId`?~~ **Settled by step 0: it does.** What is left is the
  negative case — whether an activity with no scheduled workout omits the key or carries a zero.
  A zero read as an id would link a session to a workout that does not exist, which is the
  `WORKOUT_ID_KEYS` fallback defect (§16.2a) in a new place: **a fallback is only safe while
  every key in it means the same thing.**
- **Whether a GPS run's list row carries coordinates.** Step 0's activity was indoors, so the
  absence of location fields proves nothing about a run. This is the live check the §9 location
  row actually depends on.
- Which call carries per-lap HR, and whether `maxpoly=0` suppresses the polyline.
- The reporting rule, as always: **the full tool response, verbatim, every field.** List last
  week's activities and check them against Connect.

## §4 v1.8 session B — readiness fixed, and the zones read

### B.1 Readiness — a decoder fix, a free phrase, and the source decision

**Step 0 moved this item from "find the right field name" to "fix one type check".** See §2.1:
`score` and `recoveryTime` are right, and `latest_by_timestamp` discards every snapshot because
`timestamp` is a `str` and the filter demands `int | float` (`extract.py:110`).

So B.1 is three changes, in increasing order of judgement:

1. **The decoder accepts a string timestamp.** Not by loosening the filter to "anything": a mix
   of types across snapshots must still be `MISSING`, because a `max()` over mixed types is
   either a crash or an arbitrary winner. The rule is **all numeric or all strings**, compared
   within one kind, and the ISO-8601 strings sort correctly only because they share a format —
   which is an assumption, so it is `timestamp` (UTC) that is read and not `timestampLocal`, and
   the test carries a same-day pair in both orders.
2. **`readiness_level` joins the map as a phrase row** — `level`, with `feedbackShort` available
   beside it. Free, from a request already being made, and §5 prefers Garmin's own wording to a
   number whose scale is unsourced. This is what makes the scale question non-blocking.
3. **Decision 4: the morning snapshot wins.** `get_morning_training_readiness` returns a dict or
   None and filters `inputContext == "AFTER_WAKEUP_RESET"` (read from the library,
   `__init__.py:2059`), so the row loses its decoder as it gains a source.

**The trade-off decision 4 carries, stated plainly.** The morning endpoint is the more precisely
defined source — one snapshot, taken at a known moment, which is what a check-in wants. But it
can be **empty on a day the general endpoint has data**: step 0's own reading was `list(1)` whose
`inputContext` value was not printed, so whether that single snapshot is the morning one is
unknown. §5 forbids a silent fallback between the two, so the honest shapes are:

- **one row on the morning source** (decision 4 as written), which reads `no_data` on a day with
  only a later snapshot; or
- **two rows, asked for by name** — `readiness_morning` and `readiness_latest` — which is what
  "fallback is explicit or absent" looks like when both answers are wanted.

**Recommend decision 4 as written, plus the second row only if step 0b shows the morning snapshot
is often absent.** A `None` on a day the watch was not worn is `no_data` and must not be dressed
as an error; the scale stays `"index, scale unconfirmed"` until the Connect reading settles it.

### B.2 HR zones — read-only, and a decision about where they live

`get_heart_rate_zones()` takes **no arguments** (read from the library, `__init__.py:2931`) and
**step 0 measured its shape**: five zone floors, `maxHeartRateUsed`, `lactateThresholdHeartRateUsed`,
`restingHeartRateUsed`, `trainingMethod` and `sport` — see §2.2. **One request covers all of it**,
and neither `get_lactate_threshold` nor `get_user_profile` is needed.

**The decision B needs: a zone table does not fit the metric map.** Every row in that map is one
value, one unit, one source, one `measured_on`. Zones are **five rows per sport profile and have
no date at all** — they are configuration, not a measurement. Two options:

- **(i) A new `kind` in the map** — `table` — and the rows ride in `garmin_training`.
- **(ii) A separate read tool**, `garmin_zones`, one request, returning the per-sport zone table
  plus max and threshold HR — both now known to be in the payload — and `trainingMethod`, which
  D's converter cannot be correct without.

**Recommend (ii).** §5's "the metric is the unit of exposure" is a rule about *measurements*, and
bending `measured_on` to accommodate a profile would weaken the one field that makes every other
reading auditable. (ii) also puts the zones where D will read them.

## §5 v1.8 session C — health trends over a range

**The surprise, and it moves C from expensive to cheap.** Garmin has range endpoints and the
library wraps them (all read from the library): `get_hrv_data_range(start, end)` at
`__init__.py:2038`, `get_rhr_daily(start, end)` at `1960`, `get_sleep_daily(start, end)` at
`1893` — which **auto-chunks at Garmin's own 28-day limit** and de-duplicates by calendar date.

| Range | Requests, this design | Requests, looping today's per-day rows |
|---|---|---|
| 7 days | 4 | 21–28 |
| 28 days | 4 | 84–112 |

The budget is one request every two seconds with a burst of four (`ratelimit.py:45-46`), so the
looped version is **two to three minutes of wall clock** — past the patience §5 cites as the
reason the probe is a CLI command and not a tool. Four requests is invisible.

### C.1 The contract

```
garmin_health_trend(metrics, start_date, end_date)
```

One row per day, each row naming the metric's **source** and its **granularity**
(`"daily"` or `"weekly"`), plus `requests_made` — which neither `garmin_training` nor
`garmin_health` reports today (they pass `_read_group` and return no count at all, `server.py:208`).
Decision 2's weekly stress is **labelled weekly in the row**, not silently averaged into a day.

**The range is capped and the refusal names the cap.** A default of 7 days, a maximum of 28 —
which is also Garmin's own sleep-stats chunk size, so the cap is not arbitrary.

### C.2 The structural catch, and why C is its own session

**The range endpoints are different sources with different payload layouts.** `get_rhr_daily`
returns the library's own projection — `{calendarDate, value}` pairs built from
`WELLNESS_RESTING_HEART_RATE` (read from the library, `__init__.py:1960-1985`) — while
`get_sleep_daily` returns `individualStats` rows, and neither matches the dotted paths the map
uses for the single-date sources (`hrvSummary.lastNightAvg` and friends). So:

- **Every range row starts `verified=False`**, and step 0's `--explain` is what promotes them.
  Adding them as measured because the single-date row next to them is measured would be exactly
  the 2026-10-26 failure, where a genuinely recorded path and an unrecorded mechanism were written
  into five places in one voice.
- **One metric now has two sources that can disagree**, in value *and* in type. §5 already
  requires the response to say which was read, and resting HR is the standing precedent: a `float`
  from one source and an `int` from another. This is the single most likely place for C to produce
  a wrong number that looks right.
- **`fetch.py` has no range call shape.** `_args_for` knows `CALL_NONE` and `CALL_DATE` and
  **raises** on anything else, deliberately, so that an unknown shape is a crash in a test rather
  than a plausible "something went wrong" in a conversation (`fetch.py:62-78`). `CALL_RANGE` is a
  new shape in that function and `metrics.py`'s own comment already anticipates it: *"`range`
  arrives with the trend metrics"* (`metrics.py:28`).
- **Weekly stress takes a different argument shape again:** `get_weekly_stress(end, weeks)` —
  an end date and a **count of weeks**, not a start date (read from the library,
  `__init__.py:1074`). A 7–28 day window therefore converts to a week count, and the rows come
  back dated by **week start**, which may fall outside the window asked for. The response says so
  rather than clipping silently.

## §6 v1.9 — the two reversals at the write boundary

Its own version, because both items **write to the watch** and both narrow a decision the document
has already ratified. That is the shape pace targets got in v1.6, and it is the shape that worked.

### D — HR targets on running steps

Mechanism by analogy with pace, which is the precedent worth copying exactly: **one contract
constant, one converter, feeding both the structure and the human-readable summary.**
`PACE_CONTRACT` is a single named constant with the target id read from upstream's enum rather
than written as a literal, and the bound order lives in one place — which is what made the
swapped-bounds risk a one-line fix (§9, now closed by measurement).

- Input: a zone number **or** an explicit bpm range, on a running step only.
- A zone is converted to bpm **once**, against the zones read in B (decision 3). **A zone never
  reaches the wire** — the structure carries bpm, so a stale zone table is a visible wrong number
  in a preview rather than an invisible wrong target on a watch.
- **The conversion has a measured basis as of step 0** (§2.2): zone N runs from `zoneNFloor` to
  `zone(N+1)Floor`, with zone 5's ceiling **inferred** to be `maxHeartRateUsed`. The converter
  must also read `trainingMethod` and the profile's `sport`, because the same zone number means
  different bpm under a different method and this account returned exactly one profile.
- The preview always shows bpm (decision 3).
- `HR_CONTRACT`, the sibling of `PACE_CONTRACT`, is **entirely assumed** until a live create is
  read back in Connect. Upstream's enum offers two candidates — `TargetType.HEART_RATE_ZONE = 4`
  and `TargetType.HEART_RATE_LAP = 8`, sourced upstream from `/workout-service/workout/types`
  (read from the library, `workout.py:76-88`) — and **which one carries a bpm range versus a zone
  number is the thing to settle.** Every builder upstream hardcodes `NO_TARGET`, so the target
  block is ours to construct, exactly as pace's was.
- Live check: create one easy run with an HR range, read it back in Connect, and read the watch.
  The purpose is the whole point — the load focus currently reads "high aerobic", and this is the
  instrument for keeping an easy run easy.

### E — a custom strength exercise, with a name Garmin never stores

Dumbbells only reach 5 kg and progression is time-based, so the gap is not reps and weight (still
deferred): it is that a session Mahi actually does may contain a movement **not in Garmin's
catalogue**, and today `resolve_exercise` refuses it outright — *"no Garmin exercise is named
X"* (`compose.py:481`) — which dead-ends the session rather than the step.

- The shape, per decision 1: **a free-text name, sent as an unnamed timed step plus a note.** The
  step is built by the timed builder that carries no exercise identity, so no free text becomes a
  `category`/`exerciseName`.
- **It must be an explicit kind, never a fallback.** A `custom` step kind that the caller asks for
  by name — not "if `resolve_exercise` fails, use the free text". A silent fallback would turn
  every typo of a real exercise into an unnamed step, which is the catalogue rule defeated by
  convenience. §5: fallback is explicit or absent.
- **Where the name lives is the open question.** `garmin_workouts` already takes a workout-level
  `description`, and `ExecutableStep` is `extra="allow"` upstream (`workout.py:148`), so a
  step-level `description` would pass through our layer — but **whether Garmin stores it and
  whether the watch displays it is assumed.** Decision 1's live check is exactly this: write one,
  read it back in Connect, and read the watch. Until then the name is guaranteed only in the
  preview the human approves.
- The honest framing for the preview: this step tells the watch *how long*, and tells the human
