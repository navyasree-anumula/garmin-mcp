The spine

One package imports Garmin

Every adapter — the MCP tool layer, the credential web UI, the CLI — is forbidden from importing garminconnect. Only garmin_mcp/source/ may. What it buys is a source swap: moving to the official API or a fork touches one package instead of every call site that found it convenient to reach past the boundary.

The rule existed from day one with nothing enforcing it. tests/test_layering.py now walks the AST of each adapter rather than grepping for import lines, because cli.py and web/app.py both import lazily inside functions — a grep would give a clean bill of health to a file that crosses the boundary in every handler.

Coalescing

Nine metrics, three requests

The map is the only thing in the project that knows where a metric lives, and in four of nine known cases the endpoint named after a metric is not the endpoint that answers it — VO2 max sits inside get_training_status while get_max_metrics returns an empty list.

That map is also what removes duplicate work. sources_for resolves every requested metric to its distinct sources before anything is sent, so three metrics sharing one payload cost one request. The figure of three is asserted in a test, because it is the number the read-sweep arithmetic rests on.

This is why a cache turned out to be the wrong tool. The duplication lives inside a single call, where ordinary code removes it with no TTL and nothing to invalidate.

Placement

Why the seam sits above the doorway

The cache was split in two: the seam shipped, the store did not. When the store arrives it goes above _garmin_access, never inside it. The doorway takes the cross-process lock first and then waits for a token — at 0.5 requests a second, that wait is two seconds. A hit consulted inside would pay both costs for a request it was never going to make, while holding a lock another container is queued on.

A hit as slow as a miss is not a cache.

Response contract

Five words for an answer

Every reading carries a verdict, because a nullable number invites a reader to ignore the reason. Four of the five describe absence, and they exist because “nothing came back” has four meanings that need four different responses.

The split that matters most is error against no_data. Half the map's rows were inferred rather than read off a real payload, so a path that lands on a string where a number belongs is our bug — and reporting it as no_data would make it indistinguishable from a day the watch sat on a dresser. One needs a one-line map fix; the other needs nothing at all.

VerdictMeansProducer
present There is a reading, and value carries it. readings.py
no_data A well-formed envelope with nothing in it. Says nothing about capability. readings.py
unsupported A 404, or a map row with no source. The only reliable “this account cannot” signal. fetch.py, readings.py
not_matured Empty for a metric with a known accumulation requirement — not earned yet rather than absent. none yet. No row carries a measured accumulation requirement, so nothing emits it.
error Our call or our map failed. Never Garmin's absence of data. fetch.py, readings.py

The map

Rows carry their own provenance

Metric.verified says the dotted path was read off a payload this project actually received. Five of the nine rows are inferred, and a test asserts that every unverified row states in its note what would confirm it. A map that looks authoritative while being half guesswork is the failure that flag exists to prevent: a field path is a measurement with a date on it, exactly like a verdict.

An opaque code is never interpreted. Where Garmin ships a feedback phrase, the map points at the phrase and the integer beside it is not read at all.

Three decoders exist because three payload shapes cannot be read the obvious way: primary_device picks the DTO for the watch actually being trained with and returns missing on zero or two matches rather than guessing; latest_timestamp picks the most recent of several snapshots for one day; calendar_date matches a row against the date that was asked for, because the argument returns a statistics window rather than a day.

Guards

Each rule has a test, and each test has a negative control

A call-site discipline with no test is a convention, and conventions erode the first time somebody is in a hurry. Five architectural rules are enforced by tests that walk the source rather than trusting it — and each of those tests has a companion that plants a violating file and asserts the check actually fails.

That convention earned its keep immediately. The seam's first doorway check walked only attribute and name nodes, so a file containing nothing but from .client import _garmin_access sailed through. Its own negative control caught it; it walks import aliases now.

Honest gaps

What is not built

The shape above is real and tested. These are the places where it is deliberately unfinished, each with the reason it waits.

  • capabilities.jsonOne producer, zero consumers. The probe writes it; nothing reads it. Its August verdicts are also in the old two-valued vocabulary, and two of them are wrong in opposite directions.
  • the payload storeNeeds a second consumer, measured TTLs, and a decision about health data at rest on the credential volume.
  • garmin_healthThe machinery exists; what remains is the health half of the map and two decoders training never needed, including descriptor-driven decoding for positional arrays.
  • tools.jsonTool selection is unstarted, so garmin_auth_status still cannot report which tool set is in force — an open commitment that matters more once writes exist.
  • the write pathUpstream supplies the builders, the uploads, the calendar and a 2,550-entry exercise taxonomy. What is ours is structure validation, idempotency, reversibility, and a preview that composes with zero Garmin requests.
  • serve --httpRemoved on 2026-10-24. Wired but never used, and the only reason a session-exhaustion advisory applied to this project. The server speaks stdio only, and an AST guard now holds the code to it.

The server supplies measurements and will execute validated writes. The coaching judgement happens in the conversation — a decision about tomorrow's session needs how the legs feel, how much time there is, what hurts and where in a cycle the day falls, and none of those four exists in any Garmin endpoint.
